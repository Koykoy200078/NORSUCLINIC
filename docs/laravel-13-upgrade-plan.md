## 1. Summary

- **Target:** Laravel **13.40** (13.39 when this plan was written; released 2026-03-17; PHP 8.3 – 8.5; bug fixes to Q3 2027, security fixes to **2028-03-17**). **Scope of the work: 10 → 11 → 12.70, then stop**
  (owner's decision); the owner gave the go for Laravel 13 (stage U3) on 2026-11-06 and it is **done on the branch** (13.40.0). Laravel 12 (PHP 8.2 – 8.5) gets security fixes until **2027-02-24**, which is a safe
  resting point for the clinic's PHP 8.2: the commit `3c8c434` (U3 groundwork on Laravel 12) is the last one that runs on PHP 8.2.
- **Route:** one framework step at a time, **10 → 11 → 12 (→ 13 later)**, each its own verified, reversible, deployable checkpoint,
  after a **preparation stage (U0) done on Laravel 10 itself** that removes the riskiest blockers first. Laravel 11 and 12 both run on
  the clinic's current **PHP 8.2**; only the last step (13) needs **PHP 8.3** on the clinic PC.
- **Why not jump straight to 13:** `composer why-not laravel/framework` lists **6 packages** that block Laravel 11, **9** that block 12 and **13** that
  block 13 (12 direct dependencies plus `laravel/prompts` through them), one of them **abandoned** (`laravelcollective/html`), and every skipped
  version's breaking changes would land in one commit that the 1,039-test suite could only report as "everything is red".
- **The work is dominated by four things, not by Laravel itself** (Laravel 13 is documented as a "minimal breaking changes" release):
  1. the abandoned form builder (`laravelcollective/html`, **832 lines in 83 view files**) → **rewritten for the official `spatie/laravel-html`** (owner's decision: no
     third-party fork), done on Laravel 10 with an equivalence test that renders old and new side by side;
  2. the table package `rappasoft/laravel-livewire-tables` 3.2 (held back because later versions break the 24 customised views) → **replaced by in-house plain Livewire 3 tables**
     (one shared base class + one Blade partial; owner's decision: no table package), protected by a golden-master test taken on the current tables;
  3. `spatie/laravel-permission` 5 → 6 (middleware namespace rename, in the Kernel, the Livewire persistent middleware and one test)
     and `spatie/laravel-medialibrary` 10 → 11;
  4. **PHP 8.3 on the clinic PC** (the owner's side) for stage U3 only.
- **Also in scope (owner's request):** remove packages that are proven unused and move legacy code to the newer equivalents, with evidence per item (section 13).
- **Standing rule (owner):** every UI-touching commit and every stage gets a **live browser check**; a failed one blocks the commit and the push (section 12).
- **What the upgrade buys:** the 8 `composer audit` advisories on Laravel 10.50 / medialibrary 10.15 / symfony-mime disappear (none was
  reachable here, see STATUS section 6, but Laravel 10 receives no more fixes), a supported framework until 2027 (12) or 2028 (13), and fewer third-party packages.
- **What it deliberately does not do:** no slim `bootstrap/app.php`, no Livewire 4, no Pest. **Vite instead of Mix was added on 2026-11-06 at the owner's request as its own stage, U4** (after the U0 – U3 window; decision 12).
  Laravel 11+ is documented as compatible with the Laravel 10 application structure (`app/Http/Kernel.php`, providers, `config/*.php` stay).

#### U0.4 in detail

- **Contract** (the API actually used, finding C10): keep the class `App\Livewire\LivewireTableComponent` and every child's name and namespace, so the 36 `<livewire:…>` / `@livewire` uses in 31 views do not change.
  The new base is plain `Livewire\Component` + `WithPagination`, `#[Lazy]` (placeholder `livewire.loading_skeleton`), with public `$search`, `sortBy($field)` (asc → desc → none), `gotoPage`, `getRows()`,
  `getComputedPageName()`, `builder()`, `$perPage` (10 / 25 / 50, default 10, search debounce 500 ms), `$emptyMessage`, `$showFilterOnHeader` / `$FilterComponent` / `$showButtonOnHeader` / `$buttonComponent`,
  listeners `refresh` / `resetPage` / `changeFilter` / `changeStatusFilter`; config methods `setPrimaryKey, setThAttributes, setTdAttributes, setTableAttributes, setDefaultSort, setEmptyMessage, setBuilder,
  setAdditionalSelects, setColumnSelectStatus, setQueryStringStatus, resetPage, resetPagination`; a new `App\Support\Tables\Column` with `make, label, sortable, searchable (+ callback), view, format, html, hideIf`.
  The two existing concerns become plain query steps: **`SearchesByWords`** (via `App\Support\SearchTerm`, per-column callbacks get one word) and **`SortsByUniqueKey`** (ORDER BY always ends with the model key).
1. **U0.4a golden master on rappasoft first (done 2026-11-02):** a data-driven test (reflection over the 26 components) with a fixed seed: page 1 / 2, sorted asc / desc, searched, per-page 25 → JSON fixtures of headers + per-row cell text + order under `tests/Fixtures/tables/`; green before anything is touched. Existing nets: `ListPagingTest`, `ListQueryCountTest`, `LinkCrawlTest` (loads lazy tables), the many `*PassATest` list tests.
   *As built:* `tests/Feature/Tables/TableGoldenMasterTest.php` (+ `tests/Concerns/ReadsRenderedTables.php`, `SeedsTableLists.php`, `SeedsClinicTableLists.php`). 35 rows per list (a word, "Zeta", matches every tenth). Scenarios per list: first page, pages 2 and 4, the first and the last sortable header (ascending, descending, cleared), search word, search for nothing, 25 per page, 7 per page (not offered, falls back to 10), plus the header filters and scopes the page uses (category / doctor / patient status, dispense source, lab status and patient, consultations vs certificates, "this patient only"). The reader takes the screen's *structure* (th / td text, row links and `wire:click` targets with numbers replaced by N, `.pagination`, `#perPage`, `.search-box`, the "Showing x to y of z" line, the toolbar text), **so the same fixtures must pass unchanged on the in-house tables**. Header filters are driven through the events the page's scripts dispatch (`changeFilter`, `changeStatusFilter`); `status`, `patientId` and `module` are mount parameters (they are read when the screen opens, `module` / `patientId` are locked). Re-record only on purpose: `UPDATE_TABLE_GOLDEN=1 vendor/bin/phpunit --filter TableGoldenMasterTest`, then read the git diff.
   *Checked:* recorded on PHP 8.3, replayed on PHP 8.2 and in default / reverse / random order (identical); 12 deliberate breaks each caught (default sort, per-page choices, word search, tie-break, verification list, doctor / category / patient / lab filters, dispense source, certificates module, Meds Only order), two of them found a hole in the first recording and led to the filter scenarios above. Stock Out / Used Medicines key their rows by the ledger id read as text, so rows that tie on the sorted value come back in the order of those texts (`T95` before `T147`): harmless (paging stays consistent), left as is, and the seed gives the ledger lines ids of one width so the fixtures do not depend on it.
2. **U0.4b the new base next to the old one (done 2026-11-02):**
   *As built, and where it differs from the sketch above:* the new base is **`App\Livewire\Tables\TableComponent`** (not a rewrite of `LivewireTableComponent` in place: the old and the new base must coexist while the lists are converted one batch at a time; `LivewireTableComponent`, `SearchesByWords` and `SortsByUniqueKey` are deleted in U0.4d, the new base keeps its name). A list is converted by changing three lines: `extends TableComponent`, `use App\Support\Tables\Column`, and dropping `->setQueryStringStatus(false)` (the new base never writes search / sort / per-page to the address bar; the lists that did not switch it off lose that URL sync, which is the only intended behaviour change). **Design (settled in the spike U4.0; recommended answers).**

1. **Keep every output a classic script with today's name and order.** Vite is the build engine, not a move to modules. The pre-built vendor files and the CSS concatenations are joined **byte for byte** by a small
   in-repo plugin in `vite.config.js` (what `mix.scripts()` / `mix.styles()` do today; no re-minifying, no CSS `url()` rewriting, so the theme's relative font paths keep working); the six `js()` bundles are built as **IIFE**
   (one Vite build per bundle, run by one npm script: a single Vite build cannot emit several IIFE entries, to be confirmed on Vite 8 in the spike). `<script type="module">` and `@vite()` stay for pages written later. The alternative
   (module output with all 57 inline blocks wrapped in `DOMContentLoaded`) is the riskier one and is taken only if the spike shows the classic output is not workable.
2. **Keep today's output paths and cache-busting** (`js/pages.js?id=<hash>` as `mix()` writes it), so the 67 `asset()` lines and the relative font / image URLs inside the built CSS do not change. The 13 `mix()` calls move to one
   helper that reads a small manifest the build writes (or keep the framework's `mix()` by writing the same manifest format); decided in the spike. The `?id=` hash and the existing `&v=filemtime` on `third-party.js` are then one mechanism.
3. **Static copies without a new dependency:** a node script using `fs.cpSync` (no `vite-plugin-static-copy`), same destination folders, run before the Vite builds; the output folders are cleaned by that script, not as a side effect of loading the config (C16 stays true in spirit: no build from a half-edited tree).
4. **No dev server and no HMR.** `npm run dev` today is a one-off development build, not a watcher; it stays that. So no Vite dev server on the LAN, no `public/hot` file that could point the pages at `localhost:5173`; a guard test
   asserts there is none. Script names stay `dev`, `watch`, `prod` (plus `build`) so AGENTS.md, the runbook and the bundle recipe keep working.
5. **Dependencies (confirmed by the owner when the stage starts, AGENTS.md section 5):** expected net **+1** (`vite`) and **−3** (`laravel-mix`, `sass-loader`, `resolve-url-loader`) plus the three `overrides`; `sass`, `@tailwindcss/postcss`, `tailwindcss`,

## 8. Rollback and deployment

- **Rollback of a stage:** no stage changes the database schema (no new migration is needed by any hop; package migrations are not re-published), so rollback is code only:
  `git revert` / checkout of the previous tag **and** the pre-stage copy of `vendor/`, then `php artisan optimize:clear`. The DB backup taken at the start of the stage is the safety net, not the plan.
- **Deployment of a stage on the clinic PC (owner or with help):** stop the server window → `php artisan db:backup` and copy the file off the PC → copy the project folder → pull the tagged commit → (U3 only: switch the PC to PHP 8.3 first) → `composer install --no-dev --optimize-autoloader` (needs internet once, or ship `vendor/` from the laptop) → `php artisan optimize:clear` → start with `startup-dev-environment.bat` → a short checklist: sign in, a list, a form, a PDF, the Reports tab, "Live updates" on, one backup. ## 12. Live browser checks — always (owner's standing rule)

**Rule:** no commit that changes anything a user can see or use, and no stage boundary, is "done" on green tests alone. A **live check in the built-in browser** is a mandatory gate. It also applies to "invisible" steps (framework and package hops): they get the smoke tour. A failed live check blocks the commit and the push even when the whole suite is green.

- **Setup:** the `.claude/launch.json` entry `laravel` (`php artisan serve`, `localhost:8000`) serves the branch; because `norsu_clinic` is left alone, checks run on a **scratch schema** (a rehearsal copy of the clinic dump, env overrides + guard as in the Phase 9 / 11 recipes); a `laravel-scratch` entry (port 8001) is added if needed. Logins are the QA accounts the rehearsal tooling creates on the scratch schema; passwords are never printed. Roles: admin, Staff (Nurse), doctor. Addresses: `localhost` and the laptop's LAN IP; at a deployment window the clinic PC from a second device.
- **Every check records:** the page loads (200, no blank lazy table); **no console error**; **no 4xx / 5xx** (Livewire `/livewire/update` 200, every built asset 200 — a 404 is how a removed package shows up) and **no request leaving the LAN**; a screenshot of the changed screen (kept outside the repository: the scratch schema holds real patient data); no new error in `storage/logs/laravel.log`.
- **Interactions — tables:** skeleton → rows, two-word search, sort asc / desc, per-page 10 / 25 / 50, page 2, header filters and buttons, empty message, row-actions menu, refresh after create / edit / delete, tab switching on `MedicineScreen` / `MedicineDispensingScreen`. **Forms:** render, required-field validation with old-input re-population, create, edit (model binding, selected values, Select2, date pickers, file upload, modals posted by JavaScript), delete / confirm. A quick pass at phone (375) and tablet (768) width.
- **When:** U0.2 / U0.5 / U0.6 / U0.7 → smoke tour (3 roles, every sidebar page, one table, one form, one PDF, the Live updates badge); each U0.4c batch → every table of the batch × the roles allowed, plus before / after screenshots; U0.4d → full tour after the clean-room rebuild; each U0.3 module group → every form of the group; each U0.6 / U0.8 removal → the pages that used the removed thing plus the smoke tour (login-page console first); U1 and U2 → full tour (every menu page, every table, every form once, PDF / Excel download, upload, Backups page, Live updates); before every push of the branch and at each deploy window → smoke tour from a second device and the keep / roll back decision; **U4 (Vite)** → every layout (admin app as admin / Staff (Nurse) / doctor, auth, guest, front site, queue board) in light and dark, with the console, the network list (no 404 for a built file) and the global inventory compared with the Mix baseline, then the full tour after U4.5.
